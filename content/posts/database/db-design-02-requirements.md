# DB 설계 A to Z 2강 — 요구사항 분석

[1강](/posts/db-design-01-what-is-design)에서 설계가 요구사항 분석부터 시작하는 다섯 단계라는 것을 봤습니다. 이번 편은 그 첫 단계를 다룹니다.

## 1. 왜 요구사항 분석이 가장 중요한가

설계 오류의 대부분은 SQL이 아니라 **업무를 잘못 이해한 데서** 시작합니다. "블록은 하나의 호선에 속한다"를 당연하게 받아들였는데, 실제로는 **시리즈선(동형선)끼리 블록 설계를 공유**하는 업무라면 모델 전체가 달라집니다.

## 2. 수집해야 할 정보 4가지

| 구분 | 내용 | 예시 |
|---|---|---|
| 데이터 요구사항 | 무엇을 저장하는가 | 블록 번호, 중량, 공정별 계획일/실적일 |
| 업무 규칙 | 데이터가 지켜야 할 규칙 | 실적일은 착수일보다 빠를 수 없다 |
| 처리 요구사항 | 어떤 조회·변경이 일어나는가 | 매일 아침 호선별 진척률 조회 |
| 비기능 요구사항 | 양, 속도, 보존, 보안 | 호선당 블록 500개, 실적 5년 보관, 협력사는 자기 데이터만 조회 |

초보 설계는 첫 번째만 수집합니다. 하지만 **물리 설계는 세 번째와 네 번째로 결정**됩니다.

## 3. 명사·동사 분석

업무 설명 문장에서 후보를 기계적으로 뽑는 기법입니다.

> "**협력사**는 **작업자**를 보유한다. **작업자**는 **블록**의 **공정**을 **수행**하고, 수행 시 **투입 시수**를 **기록**한다. **감독관**은 완료된 공정을 **검사**하고 **합격 여부**를 **판정**한다."

| 품사 | 후보 | 판단 |
|---|---|---|
| 명사 | 협력사, 작업자, 블록, 공정, 감독관 | 엔티티 후보 |
| 명사 | 투입 시수, 합격 여부 | 속성 후보 |
| 동사 | 보유한다, 수행한다, 검사한다 | 관계 후보 |
| 동사 | 기록한다, 판정한다 | 관계의 속성 발생 신호 |

**주의할 점**
- 동의어: "블록", "BLK", "단위블록"이 같은 것인지 확인
- 동음이의어: "공정"이 공정 마스터(취부)인지 블록별 공정 인스턴스인지 구분
- 명사라도 **식별되어야 하고 여러 건이 존재해야** 엔티티입니다. "시스템"은 명사지만 엔티티가 아닙니다.

## 4. 업무 규칙의 분류

| 유형 | 설명 | 예시 | DB 구현 수단 |
|---|---|---|---|
| 구조 규칙 | 관계와 카디널리티 | 블록은 반드시 하나의 호선에 속한다 | FK + NOT NULL |
| 값 규칙 | 속성값의 범위 | 진척률은 0~100 | CHECK |
| 유일성 규칙 | 중복 금지 | 호선 내에서 블록명은 유일 | UNIQUE(ship_no, block_name) |
| 행 간 규칙 | 여러 행에 걸친 조건 | 같은 작업자의 작업 시간은 겹칠 수 없다 | 배타 제약(PG), 트리거, 앱 |
| 흐름 규칙 | 상태 전이 | 검사 완료 후에만 도장 착수 가능 | 트리거, 앱 로직 |

이 표는 [13강](/posts/db-design-13-constraints)(제약조건 설계)의 입력이 됩니다. **업무 규칙을 문서화하지 않으면 제약조건을 설계할 근거가 없습니다.**

## 5. 모호성 제거 질문 목록

1강의 문장 "한 공정은 여러 블록에 적용된다"를 확정하려면 다음 질문이 필요합니다.

1. **최소·최대:** 공정이 적용되지 않는 블록이 있는가? (참여도)
2. **반복:** 같은 블록에 같은 공정이 두 번 적용될 수 있는가? (재작업 → PK 설계 변경)
3. **시간:** 공정 정의가 바뀌면 과거 실적은 옛 정의를 따르는가? (이력 필요 여부)
4. **소유:** 블록이 삭제되면 공정 실적도 삭제되는가? (종속성, ON DELETE)
5. **예외:** "대부분"이라고 답했다면, 나머지 경우는 무엇인가?

2번 질문이 특히 중요합니다. 재작업이 있다면 `(블록번호, 공정코드)`는 더 이상 유일하지 않으므로 차수(seq)를 PK에 추가하거나 대리키를 도입해야 합니다.

## 6. CRUD 매트릭스

프로세스와 엔티티의 관계를 표로 정리해 **누락된 엔티티와 불필요한 엔티티**를 찾습니다.

| 프로세스 \ 엔티티 | 호선 | 블록 | 공정 | 블록공정 | 작업자 |
|---|---|---|---|---|---|
| 호선 등록 | C | | | | |
| 블록 분할 | R | C | | | |
| 공정 계획 수립 | | R | R | C | |
| 실적 입력 | | R | | U | R |
| 진척률 조회 | R | R | R | R | |

점검 규칙:
- **C가 없는 엔티티** → 데이터가 어디서 들어오는지 모름 (외부 연동인지 확인)
- **R만 있고 C/U가 없는 엔티티** → 마스터 관리 프로세스 누락
- **아무 프로세스도 사용하지 않는 엔티티** → 불필요한 엔티티일 가능성

## 7. 볼륨·쿼리 프로파일

물리 설계를 위해 최소한 아래 표를 채워둡니다.

| 엔티티 | 초기 건수 | 증가량 | 보관 기간 | 주요 접근 패턴 |
|---|---|---|---|---|
| 블록 | 5만 | 호선당 500 | 영구 | 호선번호로 조회 |
| 블록공정 | 50만 | 일 3천 | 5년 | 블록번호, 공정코드+기간 |
| 작업실적 | 500만 | 일 5만 | 3년 | 작업일자 범위, 작업자별 |

작업실적은 일 5만 건, 3년 보관이면 약 5,500만 건입니다. 이 숫자가 [16강](/posts/db-design-16-partitioning)에서 **월 단위 파티셔닝**을 결정하는 근거가 됩니다.

## 8. 용어 사전

| 표준 용어 | 영문 컬럼명 | 동의어 | 정의 |
|---|---|---|---|
| 호선 | ship_no | 선번, Hull No | 건조 계약 단위의 선박 식별 번호 |
| 블록 | block | BLK | 선체를 분할한 조립 단위 |
| 실적일 | actual_date | 완료일 | 공정이 실제로 완료된 날짜 |

용어 사전은 컬럼 명명 규칙의 기준이 되며, 여러 팀이 같은 DB를 쓸 때 가장 큰 효과를 냅니다.

## 2강 정리

1. 요구사항은 데이터·업무 규칙·처리·비기능 네 가지를 모두 수집한다.
2. 명사·동사 분석으로 후보를 뽑고, 동의어·동음이의어를 정리한다.
3. 업무 규칙은 유형별로 분류해 제약조건 설계의 근거로 삼는다.
4. "같은 것이 두 번 일어날 수 있는가?" 질문이 키 설계를 바꾼다.
5. CRUD 매트릭스와 볼륨 프로파일은 누락 검증과 물리 설계의 입력이다.
