# DB 설계 A to Z 3강 — 개념 모델링 (ER 모델)

[2강](/posts/db-design-02-requirements)에서 수집한 요구사항을 이제 개념 모델로 옮깁니다.

## 1. ER 모델의 3요소

Peter Chen(1976)이 제안한 ER 모델은 세 가지로 세상을 표현합니다.

| 요소 | 의미 | 예시 |
|---|---|---|
| 엔티티(Entity) | 독립적으로 식별 가능한 대상 | 블록, 작업자 |
| 속성(Attribute) | 엔티티나 관계의 성질 | 블록 중량, 작업자 이름 |
| 관계(Relationship) | 엔티티 사이의 연관 | 작업자가 공정을 **수행**한다 |

## 2. 엔티티의 종류

| 종류 | 설명 | 예시 |
|---|---|---|
| 강한 엔티티 | 자기 속성만으로 식별 가능 | 호선(호선번호) |
| 약한 엔티티 | 소유 엔티티가 있어야 식별 가능 | 블록공정 차수(블록번호 + 차수) |
| 기본 엔티티 | 업무의 원천 | 호선, 작업자, 공정 |
| 중심 엔티티 | 기본 엔티티에서 파생된 업무 핵심 | 블록, 작업지시 |
| 행위 엔티티 | 업무 행위의 기록, 건수가 많고 자주 변경 | 작업실적, 검사결과 |

행위 엔티티는 데이터가 가장 많이 쌓이는 곳이므로 물리 설계의 주요 대상이 됩니다.

## 3. 속성의 종류

| 종류 | 설명 | 예시 | 논리 설계 시 처리 |
|---|---|---|---|
| 단순 속성 | 더 나눌 수 없음 | 중량 | 컬럼 1개 |
| 복합 속성 | 여러 하위 속성으로 구성 | 주소(시, 구, 도로명) | 하위 속성별 컬럼 |
| 단일값 속성 | 값이 하나 | 생년월일 | 컬럼 1개 |
| 다중값 속성 | 값이 여러 개 | 작업자의 보유 자격증 | **별도 테이블** |
| 유도 속성 | 다른 속성에서 계산 | 진척률, 나이 | 보통 저장하지 않음 ([10강](/posts/db-design-10-denormalization)에서 예외 논의) |
| 식별 속성 | 엔티티를 식별 | 블록번호 | PK 후보 |

**다중값 속성**을 콤마로 이어 한 컬럼에 넣는 것이 대표적인 안티패턴(Jaywalking)입니다. 개념 모델에서 다중값임을 표시해두면 이 실수를 막을 수 있습니다.

## 4. 관계의 성질

**① 차수(Degree): 참여하는 엔티티 수**
- 단항(재귀): 작업자 ─ 작업자 (반장-반원)
- 이항: 블록 ─ 공정
- 삼항: 작업자 ─ 블록 ─ 공정 (누가 어느 블록의 어느 공정을 했는가)

**② 카디널리티: 상대 엔티티와 대응하는 최대 수**
- 1:1 — 호선 ─ 계약서
- 1:N — 호선 ─ 블록
- N:M — 블록 ─ 공정

**③ 참여도(Participation): 최소 수**
- 전체 참여(필수): 모든 블록은 반드시 호선에 속한다
- 부분 참여(선택): 모든 작업자가 반장인 것은 아니다

카디널리티와 참여도를 합쳐 **(최소, 최대)** 로 표기하면 모호함이 사라집니다.

```
호선 (1,1) ─── 소속 ─── (0,N) 블록
  → 블록은 정확히 1개 호선에 속함
  → 호선은 블록이 0개 이상 (수주 직후에는 블록이 없음)
```

## 5. 삼항 관계는 이항 관계 셋과 다르다

"작업자 A가 블록 B의 공정 C를 수행했다"를 이항 관계 셋으로 쪼개면:

- 작업자 ─ 블록: A가 B에서 일했다
- 블록 ─ 공정: B는 C를 거친다
- 작업자 ─ 공정: A는 C를 할 줄 안다

이 셋을 조합하면 "A가 B의 C를 했다"가 **참인지 알 수 없습니다.** A가 B에서 용접을 했고, B는 도장을 거치고, A가 도장도 할 수 있어도 A가 B의 도장을 한 것은 아닐 수 있습니다. 세 엔티티가 동시에 결합된 사실은 **삼항 관계로 모델링**해야 합니다. 이 원리는 [9강의 5NF](/posts/db-design-09-4nf-5nf)와 직결됩니다.

## 6. 엔티티인가, 속성인가, 관계인가

| 판단 질문 | Yes면 |
|---|---|
| 그 자체로 다른 속성을 가지는가? | 엔티티 |
| 여러 엔티티가 공유하는가? | 엔티티 |
| 독립적으로 생성·삭제되는가? | 엔티티 |
| 시간에 따라 이력이 필요한가? | 엔티티 (또는 관계) |
| 두 엔티티 사이에서만 의미가 있는가? | 관계 또는 관계의 속성 |

예시: "블록의 도장 색상"
- 색상 코드와 이름만 있다면 → 블록의 속성
- 색상마다 도료 제조사, 단가, 건조 시간을 관리한다면 → 도료 **엔티티**, 블록과 관계

## 7. 재귀 관계

```
작업자 (0,1) ─── 반장이다 ─── (0,N) 작업자
```
같은 엔티티 사이의 관계입니다. 역할 이름(반장, 반원)을 반드시 붙여야 의미가 명확해집니다. [17강 계층 구조 모델링](/posts/db-design-17-hierarchies)의 출발점입니다.

## 8. 예제 도메인 개념 모델

```
[협력사] 1 ──보유── N [작업자] ──┐
                        │ (반장)  │ 재귀
                        └─────────┘
[호선] 1 ──소속── N [블록]
[블록] N ──적용── M [공정]  → 관계 속성: 계획일, 실적일, 차수
[작업자], [블록], [공정] ── 수행 (삼항) → 관계 속성: 작업일, 투입시수
[감독관] ──검사── [블록공정]  → 관계 속성: 판정, 검사일
```

마지막 줄은 **관계(블록공정)에 대한 관계**입니다. 이런 형태가 보이면 해당 관계를 엔티티로 승격(연관 엔티티)시켜야 한다는 신호입니다.

## 3강 정리

1. ER 모델은 엔티티·속성·관계로 구성되며, 관계에도 속성이 있다.
2. 다중값 속성은 별도 테이블 후보이며, 콤마 저장은 안티패턴이다.
3. 카디널리티(최대)와 참여도(최소)를 함께 표기해야 모호하지 않다.
4. 삼항 관계는 이항 관계 셋으로 분해할 수 없다.
5. 관계에 다시 관계가 붙으면 연관 엔티티로 승격한다.
